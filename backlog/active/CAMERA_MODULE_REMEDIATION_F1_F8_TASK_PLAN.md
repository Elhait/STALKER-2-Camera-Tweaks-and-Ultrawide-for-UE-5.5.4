## Governing invariant and boundaries

Shared raw observation establishes camera/source provenance and lifecycle evidence. The coordinator establishes ownership. Only an enabled correction belonging to the effective owner may change camera output. `Enabled=false` removes that module's correction, not the shared observation needed by other modules and not another module's ownership.

`RuntimeState` remains the integration owner. Do not introduce a universal camera framework, change Overlay/DirectComposition, alter native rapid `EXIT → ENTER` semantics, treat the native-control animation hitch as a mod defect, or add timeouts, frame counters, debounce, or hard-coded FOV thresholds to decide semantic ownership. Preserve existing staged/unstaged user changes and the entire `research/` tree. Do not reset, revert, checkout, stage, or commit as part of this plan. No game launch without separate authorization.

The current camera-writer resolver validates RSI as input source and RBX as output object. The cinematic ENTER resolver validates an FOV callsite, **not** a camera-source identity. Consequently a last-observed writer pointer is not proof that it is the ENTER camera. A source-bound correction must fail closed until the ENTER↔writer relation is established. This is an evidence gate, not permission to use an unconfirmed source.

## Authoritative state contracts to establish

1. **Raw camera observation:** before module correction gates, capture validated native writer input FOV, source identity (RSI), output identity (RBX), readable aspect/flags, observation sequence, and an observation epoch. Publish independently of all three module `Enabled` settings. An epoch advances on observed source/output replacement or explicit lifecycle invalidation; elapsed time does not establish freshness. A pointer/epoch pair still cannot prove an *unobserved* camera switch.
2. **ENTER binding:** an accepted cinematic generation may consume a raw baseline only when a validated source/output or object relation proves it belongs to the camera entering that generation. Determine that relation from current callsite/object evidence before coding it. If static evidence is insufficient, specify a bounded read-only ENTER/first-writer provenance capture for a separately authorized runtime session. Unknown/mismatched provenance yields native pass-through for source-dependent correction, never retention against an assumed source.
3. **Cinematic selection:** accepted ENTER owns an immutable effective Mode/FovMode/Enabled selection, authored native FOV, optional proven raw baseline, established target, bound source/epoch, and lifecycle generation. `FovMode=GameplayHorPlus` uses the raw native baseline and Cinematics' own transform; it does not invoke Gameplay correction. Requested settings may change separately.
4. **EXIT/recovery:** each EXIT may consume one active accepted cinematic generation. A shared source-bound native-recovery result determines when `CinematicExiting` ends; Gameplay-specific transform runs only if Gameplay correction is enabled. Different or unknown source cannot complete source A's recovery merely by matching FOV/flags. An explicitly validated source-replacement path may rebind; no implicit numeric rebind.
5. **Dialogue accepted start:** bind correction activation to the accepted candidate's source/epoch and captured Mode. Each active output write verifies that provenance without assuming a Gameplay writer ran first. Mismatch disables that correction path and requires a new accepted start; it does not transfer coordinator ownership.
6. **Settings publication:** per-module requested settings have a coherent publication generation. Effective Cinematics and Dialogue selections are lifecycle-scoped; Gameplay effective state has its existing next-writer transition. Define a linearization point for OFF and safe handling of in-flight callbacks so that a completed OFF mutation cannot be followed by a new correction write. A previously written camera value is a separate restoration/UX contract, not evidence of a new post-OFF write.

### Minimal read-only capture specification — not implemented

One separately authorized diagnostic artifact/session, bounded to the first accepted cinematic ENTER (and, if necessary, one later accepted ENTER after a source change), should retain a **one-record pre-ENTER writer snapshot** and record only the first post-ENTER writer plus source/output-identity changes until EXIT. Duplicate/rejected ENTER does not arm a second capture. Records are event-driven; no per-frame stream, no camera writes, no new correction, no hook of game presentation.

1. **Session identity:** installed game-image SHA-256, diagnostic artifact SHA-256/profile, resolved ENTER/writer/aspect-store RVAs, QPC frequency, and process/thread IDs. This prevents a cross-image or cross-artifact relation from being promoted to a current-image contract.
2. **Pre-ENTER writer record:** sequence/observation epoch, QPC, thread ID, raw `XMM0`, RSI source pointer, RBX output pointer, and guarded source aspect/flags validity. Capture the last writer record and the last *observed identity change*; this is context only, never authority for ENTER binding.
3. **Accepted ENTER record:** new cinematic generation, QPC/thread ID, raw and resulting `XMM0`, raw pre-call `RCX` (candidate first-call argument/receiver) and `RSI` (later `MOV RCX,RSI` candidate), and the pre-ENTER writer sequence/epoch. Label these as **raw registers of unproved object type**. Do not dereference them merely because they look like pointers. Record rejected ENTER only as a count.
4. **Post-ENTER writer record:** first writer invocation after that accepted generation, QPC/thread ID, raw `XMM0` before correction, RSI, RBX, sequence/observation epoch, guarded source aspect/flags validity, and whether subsequent relevant writer source/output identities change before EXIT. Record the actual writer output classification without changing it.
5. **Conditional candidate bridge:** the aspect-store target RAX and its already validated `[RCX+0x18]→+0xF8` chain are useful only if a current-image static call/object relation places that store in the same accepted ENTER lifecycle. If such a relation is established, log the aspect-store target identity and the necessary chain pointers once at that boundary, with QPC/thread/generation. Otherwise omit that event and all extra object-field reads. Do not scan arbitrary player/controller/manager offsets.

**Decision rule for the capture.** Direct pointer equality between a validated ENTER-side camera object and writer RSI, together with a proven lifetime/owner relation, could establish a source-binding contract. An ENTER-side output object similarly must be tied to writer RBX through a validated relation. Equality of raw, untyped registers or mere pre/post temporal ordering is only a candidate; inequality falsifies that particular direct-pointer candidate but not every possible indirection. If no validated bridge emerges, retain the fail-closed disposition and do not implement source-dependent retention by guessing. No diagnostic code, ASI or runtime experiment was created in Stage 1.

## Settings semantics and failure behavior

- **Gameplay ON→OFF:** stop new Gameplay correction after the completed OFF transaction; raw observation and Cinematics/Dialogue ownership remain. Gameplay aspect/FOV already written to the game is a separate restoration decision. **OFF→ON:** apply at the next eligible Gameplay writer boundary, not during another owner's correction.
- **Cinematics ON→OFF:** keep lifecycle/coordinator, stop new Cinematics FOV/aspect writes coherently and prevent stale target reuse. Do not claim an immediate native rewrite of an already-written FOV. **OFF→ON:** correction remains deferred until the next accepted ENTER.
- **Dialogue ON→OFF:** retain phase/source observation and owner, stop new XMM1 correction after the completed OFF transaction. **OFF→ON:** remain unarmed during the current Dialogue; use stored Mode at the next accepted start. `Disabled` remains an active policy distinct from OFF.
- An ordinary last-second atomic recheck is insufficient for the strict post-OFF guarantee if a setter may finish between check and output write. Before implementation, verify the actual callback/mutation thread model and choose a module-local serialization or in-flight publication protocol with a documented linearization point; do not hold arbitrary locks across game code or foreign ABI continuation.
- Failure to validate source, epoch, native endpoint, or coherent settings snapshot results in native pass-through/no correction and no ownership transfer based on numeric resemblance alone. A failed observation capability disables only correction paths that require it.

**Authority and scope.** This section supersedes earlier F8 coverage descriptions, not historical findings or camera policy. ### 1. Current F8 state and evidence standard

The current `test.cmd` registers **56 compiled/executed harnesses**. The shared lifecycle transaction now accepts/generates ENTER and selects the numeric baseline/target from explicit validated inputs. `ObserveCinematicAspectStore` owns the event policy/association result; the adapter performs the external native write. The lifecycle scenario then calls the same `ProcessCameraWriter` once for each writer event, asserting actual returned cinematic output/action and read-only state after events. Thus accepted ENTER selection, aspect policy result and tested Cinematic writer output have scoped PE coverage. Register capture, native aspect write, actual XMM0 application and active projection remain outside the harness.

At C2, `ProcessCameraWriter` owns shared writer observation and F4 retirement, HorPlus recovery sampling/interpolation/endpoint completion, no-owner cleanup, active Cinematic policy/output, and Gameplay HorPlus Enabled/Mode dispatch including source-context observation, FOV observation and baseline publication. `ReplayManualTransition` applies returned XMM0 and provides ABI-safe reads/callbacks and diagnostics, but still owns the engine-dependent AspectRecalculation recovery endpoint, atomic aspect handoff, Gameplay mode/restoration engine effects, `ReplayManualTransitionOriginal`, and native replay/early-return mechanics. Do not treat C2 as completion of Batch 1 or all writer dispatch.

Coverage labels in this plan are **scoped claims**: production-equivalent (PE) means the hook and scenario call the same state/output transaction for the named path; shared production primitive (SP) means a real helper is tested but its hook composition is not; model-only (M) means the harness reproduces at least one decision or transition; runtime-only (R) is evidence from an integrated game capture, not an offline harness; missing (X) has neither. A harness containing PE and M portions receives its strongest *narrowly named* label below, with the M gap stated. No harness gets a blanket PE claim for an entire module.

### 4. Highest-risk coverage gaps, in migration order

1. **Same callback F4→Gameplay output:** the current F4 tests prove retirement/cancellation, then separately call a Gameplay helper. A missing hook fallthrough still passes.
2. **Recovery authority/completion/output:** HorPlus interpolation, owner rejection, no-owner cleanup, AspectRecalculation endpoint and atomic handoff are split between transaction, hook and primitive tests. Source and failed-read/write ordering can be wrong despite green helpers.
3. **Gameplay AspectRecalculation and mode restoration:** `ReplayManualTransitionOriginal` owns rearm and writes; no scenario reaches it via the same semantic transaction used by production.
4. **Dialogue callback lifecycle/output:** helper tests cannot detect a wrong phase, Enabled/owner gate, missing XMM1 commit or unwanted Candidate→Active under Cinematic.
5. **ENTER/EXIT preparation and settings composition:** shared lifecycle primitives receive preselected target/next state; wrong baseline selection, generation publication or no-owner hook cleanup can be masked.
6. **F6 end-to-end ordering:** the gate test uses modeled output and the writer test composes a separate resolver. They prove synchronization/primitive behavior, not the final output path for all three modules.
7. **Diagnostic equivalence across composed events:** local capture/gate tests exist; whole-sequence state/output comparison through the shared transactions is absent.

Retain lower-level primitive tests for local math, finite/range checks, source contracts and failure classifications. Remove a model-only integration test only after an event-driven PE scenario asserts the same invariant and deliberate break of production wiring makes that scenario fail.

### 6. Proposed final transaction architecture

```text
SafetyHook adapter: register/ABI extraction, validated safe reads, RIP/trampoline
    → event input with explicit value+validity and opaque pointer identities
    → RuntimeState-owned gate + production event transaction
         ENTER / aspect store / EXIT / Dialogue boundary / setting / writer
         state observation → owner routing → policy → ordered effect request
    ↔ narrow engine operations: read aspect+flags; write aspect only;
                                write aspect+flags; optional viewport aspect
    → production continuation/commit after operation success or failure
    → result: FOV/aspect decision, action, state outcome, next hook action
    → adapter writes XMM0/XMM1 or follows original RIP/trampoline
```

`RuntimeState` remains owner of settings, coordinator, stores, locks and hook lifetime. Use small event-specific transactions, not a second framework or one giant universal dispatcher. Existing `ProcessAcceptedCinematicEnter/Exit`, `ObserveCinematicAspectStore`, `ApplyCameraSetting` and `ProcessCameraWriter` are starting seams. Add a Dialogue boundary transaction only when migrating that hook. The writer orchestrator may call internal recovery, Gameplay, restoration and AspectRecalculation steps; the hook must never retain an independent copy of their decisions.

Introduce a narrow engine-I/O port **only when a migrated path needs it**. Its operations expose safe field read status, aspect-only write result, aspect+flags write result and viewport aspect acquisition if relevant. They do not implement `RunGameplayPolicy`, `CompleteRecovery`, `ResolveCinematic` or state mutation. A harness fake returns configured read/write outcomes and records the exact operation order; it cannot decide camera policy. The production implementation calls the existing validated safe memory helpers. Keep the gate across semantic decision, requested engine write and state commit so F6 OFF-return semantics hold. If a read/write failure produces an early return, return that exact effect/result and assert that no later commit happened. A small continuation result after the effect is preferable to adding speculative cached fields to `CameraWriterInput`.

The scenario runner supplies only public semantic events (`SetCameraSetting`, `CinematicEnter`, `AspectStore`, `CinematicExit`, `DialogueBoundary`, `Writer`) and opaque fixture pointers. It can configure the fake engine's memory/read/write outcomes; it cannot call `SetCoordinator`, `CaptureRecoveryOwner`, `BeginGeneration`, `ArmExclusion`, or mutate correction fields directly. Fresh process-equivalent state per scenario; assertions after **each** event cover final FOV/aspect or pass-through, action, coordinator, generation, association, continuation, recovery owner/exclusion/handoff, epochs and write attempts. A scenario may read state through a read-only snapshot. Test fixture values do not prove native pointer provenance.

### 8. Runtime-only boundary after F8

Automated scenarios must not emulate SafetyHook or UE internals. Hook installation, signature resolution, register/ABI correctness, actual instruction replay/RIP change, native memory protection and real pointer validity, exact engine object/lifecycle semantics (including F5 A↔B and F7-B stale EXIT), real scheduling beyond controllable transaction order, downstream projection/rendered framing and user-visible image remain integrated-runtime evidence. An offline fake write proves that our transaction requested and handled a successful/failed write correctly; it does not prove that the game exposes a writable field or consumes it for the active view. ### 15. Migration risks and review triggers

- **Ordering drift:** initial writer aspect/flags capture is not a substitute for fresh reads after a native write/mode transition. Assert operation sequence and failed-write retry.
- **False PE claim:** direct primitive calls after a writer transaction can produce the right FOV even if the hook returns early. One semantic event must produce the final result.
- **Privileged fixtures:** direct coordinator/owner/association/exclusion writes bypass lifecycle acceptance. Build those states through ENTER/aspect/writer/EXIT/recovery events.
- **Incorrect identity:** RSI pair changes are not world lifetime; Dialogue accepted A need not equal legitimate Active/Exiting B; ±1° is neither source proof nor recovery endpoint.
- **Concurrency/regression:** preserve gate → Dialogue mutex → camera-state mutex, defer slow logs after unlock, and commit state only after required safe native effect succeeds.
- **Scope creep:** do not turn the port into a policy fake, split `runtime.cpp` into a new framework, modify `src/overlay`, or adopt F2/F3/F5/F7-B heuristics. An unexpected engine dependency is a stop condition for that step, not permission to rewrite policy.
