## Notation and coverage

`R` means `src/plugin/runtime.cpp`; line numbers refer to the inspected 2026-10-11 working tree. A = passive observations; B = resource/hook/synchronization implications; C = experimental behavior changes or forensic discovery. Mixed tools retain both classifications where their branches differ. `Review` is a disposition, not a fourth safe-production category. Availability is current, not promised after migration. OFF costs are source-observed operations; no timings were measured.

The tables inventory project-owned diagnostic gates and their build/test entry points, including historical source gates still present. Vendor internal debug macros, generic test seams and functional feature macros are explicitly separated at the end.

## Build and test references

- `build.cmd:23–49`: defines/profile selection. `SUPPORTED_DIAGNOSTICS_DEFINE` duplicates env-selected Zoom/FOV/snapshot flags; not an independent runtime gate. Final passive unification should remove the migrated flag variables and obsolete switches, while retaining forensic opt-in and compatibility of supported wrapper/output overrides.
- `tools/build/build-diagnostic.cmd`: sets the diagnostic profile and calls the production entry point. Recommended transition: retain a compatibility wrapper/output identity initially, with the same passive diagnostic capability as ordinary production; document its remaining purpose. Removal or public renaming requires an explicit decision.
- `tools/build/build-gameplay-fov-source-diagnostic.cmd`: already clears diagnostic profile and builds the ordinary implementation to an isolated path; its name alone does not enable extra compile-time traces.
- `tools/build/build-overlay-settings.cmd`: compatibility alias to ordinary production; not a diagnostics selector.
- `test.cmd:288` and `tests/runner/native_runtime_evidence.ps1:78–80`: compile actual adapters with the diagnostic flags. After migration, remove obsolete flags and preserve actual-source integration, Diagnostic OFF/ON scenarios and inventory checks. Do not substitute rewritten adapters.
- `tests/runner/runtime_native_adapter_inputs.ps1`: uses the current explicit `build.cmd` source registry, excludes `runtime.cpp` and `dll_entry.cpp` because the harness includes the real adapter TU once. Do not modernize that registry in this task.
- `tools/build/build-language-state-watcher.cmd`, `build-targeted-language-candidates.cmd`, `build-stratified-language-watcher.cmd`: separate forensic executables. Keep them out of ordinary ASI compilation.

## Functional/test gates that must not be mistaken for diagnostics

`OVERLAY_PRODUCTION`, `OVERLAY_SETTINGS_FRONTEND`, `OVERLAY_COMBINED` and legacy `OVERLAY_RENDERING_POC` select product/integration boundaries. `SIGNATURE_SCANNER_TEST`, `SAFETYHOOK_TEST_VIRTUAL_PROTECT`, `RUNTIME_ADAPTER_ZOOM_SAFE_READ`, `RUNTIME_ADAPTER_INITIALIZE_THREAD_CALL` and `RUNTIME_ADAPTER_INITIALIZATION_FAILURE_CLEANUP` are test boundaries. They are not candidates for blanket macro removal. Vendor assertions/log-level/platform macros are not project runtime instrumentation.

Mandatory safety/error logging, shared camera snapshots, native Zoom state, `matchGameplay*` lifecycle facts and freshness/publication sequences are deliberately included in the inventory as preservation boundaries. Their presence when Diagnostic Mode is OFF does not authorize turning them off.
