# v2.0.0 → v2.0.1 working-tree difference report

Date: 2026-09-28. Baseline: repository tag and current `HEAD` both resolve to `56dbeb9788154da84f47fed8138945afc401e823` (`v2.0.0`). This report describes the current candidate; v2.0.1 has not been committed, tagged or released.

## Scope and comparison boundary

At this review, `git diff v2.0.0` contains 58 paths, 6,079 insertions and 450 deletions. Most candidate changes are staged; this report and `TESTING_AND_RESEARCH.md` also have unstaged updates from this review. There are no untracked paths. This count includes this report. The ignored root build output `STALKER2CameraTweaks.asi` is not part of the repository diff.

This is a code, safety, diagnostics, validation, research-record and visual-asset update. It does not add public camera modes, change INI defaults/schema, redesign Overlay interaction, or edit localization catalogs or the Hor+ math. It does correct runtime camera lifecycle handling after cinematic EXIT: transitional FOV remains pass-through, while a first post-EXIT sample already at the validated native target resumes Gameplay HorPlus immediately. The other material product change is improved Overlay fault isolation and discovery/validation of the real graphics presentation path before renderer/input activation.

## Executive summary

The v2.0.1 candidate hardens the optional Overlay/DXGI/D3D12 subsystem after a user-observed startup crash in a graphics-wrapper stack. Camera core remains independent. The repair does not claim to identify one universal cause for all native graphics crashes; it addresses concrete lifecycle, hook-ownership, resource-lifetime and failure-isolation risks, then adds an independent shared-factory-table observation route alongside the existing export hooks. A separate Gameplay recovery correction fixes two distinct post-cinematic cases without changing the camera transform formula.

The Overlay follows a gated lifecycle: early observation → validated real application swapchain/device/queue → core ready and two successful Presents → renderer activation → input activation. A temporary seed factory supplies only COM factory interfaces for safe shared-table hook coverage; it is never treated as a renderer target and creates no device, window, swapchain, queue, or GPU workload. A lightweight startup journal is now enabled in the production build; invasive forensic timeline tracing remains opt-in.

## Functional and architectural differences

### 1. Optional Overlay failure isolation

Overlay startup and runtime-only failures are isolated from Gameplay, Cinematics and Dialogue initialization. The optional-startup boundary catches Overlay initialization failures and leaves the camera core available for INI-based configuration. Exceptions from the runtime settings callback are contained rather than escaping through the API boundary. Native DXGI callbacks retain native forwarding behavior and exact results where the Overlay path is unavailable or declines work.

Files: `src/plugin/optional_overlay_startup.hpp` (new), `src/plugin/runtime.cpp`, `src/plugin/runtime_settings.hpp`, `docs/ARCHITECTURE.md`, `docs/SAFETY_INVARIANTS.md`.

### 2. DXGI hook ownership and ABI safety

The DXGI layer now defines SDK-native callback types and method slots explicitly, selects the canonical system DXGI module, and stores process-resident hook/table ownership. Hook publication and callback leases are synchronized; original methods are captured/reused without retaining COM objects. Shared tables are validated for SDK-bounded extent and executable image-backed methods, then pinned with their owning modules for process lifetime. Private vtable tail entries are preserved. Resize nesting records the final outer native result instead of letting an inner failure erase later successful evidence.

Files: `src/overlay/dxgi_abi.hpp` (new), `src/overlay/dxgi_hook_registry.hpp` (new), `src/overlay/dxgi_module_selection.hpp` (new), `src/overlay/dxgi_resize_nesting.hpp` (new), `src/overlay/discovery_runtime.cpp`, `src/overlay/discovery_evidence.cpp`, `src/overlay/discovery_evidence.hpp`.

### 3. Independent shared factory-table bootstrap

Existing DXGI export hooks remain supplemental discovery. They are no longer the sole readiness prerequisite. Startup creates a seed factory through the retained native `CreateDXGIFactory1` route, queries supported factory interfaces widest-first, validates and hooks safe shared image-backed tables, and releases the seed after installation. A recursion guard prevents seed creation from re-entering export-result discovery.

Only successful real `CreateSwapChain*` calls can establish a pending target, with the callback's actual device/direct-queue association. Nested proxy/native callback paths deduplicate the same canonical swapchain identity without merging unrelated objects. The seed cannot itself become the pending or active renderer target. Failure to prove safe shared-table coverage leaves the Overlay unavailable while camera core continues.

Supported coverage is deliberately bounded: a wrapper that uses an unrelated private per-instance factory table while bypassing export callbacks is not claimed as covered. Already-created swapchains are not recovered by this bootstrap. There is no enumeration, memory scan, polling, blind re-hook, filename-specific handling, startup sleep, synthetic target, or GPU warm-up workload.

Files: `src/overlay/factory_observation_coverage.hpp` (new), `src/overlay/nested_factory_creation.hpp` (new), `src/overlay/discovery_runtime.cpp`, `src/overlay/discovery_evidence.*`, `docs/ARCHITECTURE.md`, `research/reports/DXGI_FACTORY_TABLE_BOOTSTRAP_IMPLEMENTATION_2026-09-28.md`.

### 4. Validated target and delayed activation

The previously accepted lifecycle remains intact. A real successful swapchain-creation callback supplies target ownership and device/queue association. Existing evidence validation gates pending-target acceptance; two successful native Presents are required before renderer activation. Renderer and input activation remain delayed until the camera core and target evidence are ready. TEST/DO_NOT_WAIT and other rejected/failed native paths do not gain Overlay GPU work. Multiple swapchains/devices remain independently identified and serialized; the change does not reintroduce the disproven cross-swapchain-resource hypothesis.

Files: `src/overlay/discovery_runtime.cpp`, `src/overlay/discovery_evidence.*`, `src/overlay/renderer_runtime.*`, `src/overlay/renderer_wait_policy.hpp` (new), `tests/overlay/*`.

Runtime logs exposed a resize recovery regression: the renderer entered `Resizing`, but the Present call site invoked `Render()` only in `Ready`, so the next-Present backbuffer rebuild could not run. Input remained activated and toggles hid the system cursor, while no first Overlay frame was recorded. The gate now admits render work in both `Ready` and `Resizing`, but not after terminal disable; renderer-lifetime assertions cover all three states. The supplied latest camera log does not establish first-frame or cursor behavior for the current candidate, so those Overlay outcomes remain unconfirmed here.

### 5. Renderer, D3D12 and ImGui backend safety

Renderer lifecycle now handles same-window replacement, resize and teardown with explicit resource/evidence transitions. GPU waits are bounded; if completion cannot be established, resources that may still be GPU-owned are retained rather than freed unsafely. Terminal renderer failure disables the affected Overlay path and cannot silently re-arm input. Partial initialization/teardown is hardened. The project-local ImGui DX12 backend checks upload/allocation/map/signal paths, synchronizes uploads against a known completed frame slot, and handles partial backend state safely.

This does not promise recovery from arbitrary access violations, SEH faults, driver hangs or device-removal behavior; those remain outside deterministic offline proof.

Files: `src/overlay/renderer_runtime.cpp`, `src/overlay/renderer_runtime.hpp`, `src/overlay/renderer_wait_policy.hpp`, `external/imgui/backends/imgui_impl_dx12.cpp`, `external/imgui/backends/imgui_impl_dx12.h`, `external/imgui/backends/imgui_impl_dx12_safety.h` (new).

### 6. Production startup journal

The canonical production profile records a bounded startup timeline to `STALKER2CameraTweaksStartup.log`: attach/worker, bootstrap begin/result, supplemental export coverage, discovery readiness/source, camera-core readiness, first real factory/swapchain, pending target, first and second successful Presents, renderer/input activation, and first Overlay frame. DllMain records only lightweight fixed-buffer/timestamp data; file I/O is deferred to the worker. No jump decoding, export-chain chasing, module archaeology, or per-Present journal spam runs by default. The intrusive forensic timeline is available only with the explicit `CAMERA_TWEAKS_STARTUP_TIMELINE=1` diagnostic opt-in.

Files: `src/diagnostics/startup_journal.hpp` (new), `src/diagnostics/startup_timeline.hpp` (new), `src/plugin/dll_entry.cpp`, `src/plugin/runtime.cpp`, `build.cmd`.

### 7. Post-cinematic Gameplay HorPlus recovery

The v2.0.0 EXIT path returned the HorPlus coordinator to `Gameplay` immediately. A previous v2.0.1 repair instead held native pass-through until the Dialogue recovery tracker observed a depart-then-return sequence. That was too strict for Gameplay: a supplied runtime trace showed the first same-source gameplay writer sample already matched the saved native EXIT target (`90.6557`, gameplay flags `0x4`, aspect `3`), yet HorPlus stayed suspended until ADS moved the FOV away and back.

The current candidate uses a Gameplay-specific recovery predicate. It requires a readable camera sample, the validated camera source, gameplay flags, a finite positive aspect, and a valid FOV matching the saved native EXIT target within the existing epsilon. When the pre-cinematic native `GameplayBaseline` still owns that source, the matching first sample is sufficient; a replaced source must obtain the existing source-bound recovery evidence. Otherwise the writer returns the transitional/ambiguous input unchanged without transforming it or publishing it to `GameplayBaseline`. Once Gameplay resumes, ordinary ADS/modifier FOV updates continue through HorPlus. The Dialogue exclusion retains its original depart-then-return contract and is not cleared by immediate Gameplay recovery.

The focused regression covers both `90 → 106.688 → EXIT → 106.688 → 90 → 106.688` and an already-native first post-EXIT sample, plus ADS, a later native FOV change, 16:9 through 48:9 aspects and invalid/source-mismatch rejection. The test verifies that `106.688` is not transformed again to `122.044` in the transitional branch.

Files: `src/gameplay/gameplay_state.hpp`, `src/gameplay/gameplay_state.cpp`, `src/plugin/runtime.cpp`, `src/dialogue/dialogue_state.hpp`, `src/dialogue/dialogue_state.cpp`, `tests/cinematics/horplus_post_exit_recovery_harness.cpp` (new), `tests/cinematics/coordinator_recovery_harness.cpp`, `tests/dialogue/post_cinematic_exclusion_harness.cpp`, `test.cmd`, `docs/SAFETY_INVARIANTS.md`.
