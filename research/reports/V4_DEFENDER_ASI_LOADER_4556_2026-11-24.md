# v4.0.0 — локальне дослідження Defender і ASI Loader 4556

**Статус** — статичне порівняння релізних файлів виконано. Причину блокування на рівні категорії визначено за кодом Windows. Окрема детекція Defender і конкретний файл на ПК автора багрепорту залишаються непідтвердженими. [План](../plans/V4_DEFENDER_ASI_LOADER_4556_2026-11-24.md)

## Що встановлено

Windows SDK називає код 4556 `ERROR_SYSTEM_INTEGRITY_REPUTATION_MALICIOUS`. Системний текст прямо вказує на Application Control і репутацію файла. Це пояснює категорію відмови, якщо Loader передав Win32-код без перетворення. Текст багрепорту окремо згадує Defender, але не містить назви загрози, шляху, ідентичності файла чи події політики. Тому не встановлено, чи було два незалежні спрацювання або два повідомлення про одну відмову. Читання локальних каналів Defender та Code Integrity повернуло відмову доступу. Подій із ПК автора звіту тут немає.

## Порівняння релізів

Контрольні зразки прочитано з локальних релізних ZIP. SHA-256 архівів і їхніх ASI та повні статичні звіти збережено разом. v4 у ZIP збігається з окремим релізним ASI в `release-assets`. Відповідність завантаженому автором файлу не встановлено. [PE v3.2.2](../evidence/v4-defender-asi-loader-4556-2026-11-24/v3.2.2-pe.txt) · [PE v4.0.0](../evidence/v4-defender-asi-loader-4556-2026-11-24/v4.0.0-pe.txt)

- Обидва файли є x64 DLL, з linker 14.44, однаковими DLL characteristics і сімома секціями. `.text` має права Execute/Read в обох файлах. Немає PE certificates, експортів чи delay imports. TLS, unwind та relocations є в обох файлах. Entry point і розміри секцій змінилися. Розмір ASI зменшився з 3 567 104 до 3 404 800 байтів, секція ресурсів виросла.
- Набір із семи DLL залежностей однаковий. Єдиний доданий іменований імпорт — `OutputDebugStringW`. Його додає повідомлення про резервний лог при конфлікті доступу. Це зміна журналювання. Даних, які пов'язують її з класифікацією, немає.
- Для релізної цілі порівняний CMake зберіг статичний CRT, `/O1`, `/MANIFEST:NO` і перелік бібліотек. Крім версії, додані визначення для провенансу Dialogue і точки активації blend, яку використовує provider handoff. Наявних PE і CMake недостатньо для відтворення точного середовища двох релізних збірок.
- Реалізація `safetyhook.cpp` між базою v3.2.2 і релізним комітом v4 ідентична. У заголовку додано лише доступ для читання даних trampoline. v4 використовує наявний механізм hooks на додаткових точках камери. У переглянутих відмінностях не знайдено повернення попередніх дефектів SafetyHook або нової залежності, що пояснює повідомлення 4556. Це статичне спостереження, оскільки встановлення hooks у цьому дослідженні не запускалося.

## Рішення за доступними доказами

Для зазначеного коду найбільш конкретний висновок — відмова за правилами репутації Windows. Причину, через яку політика дала цей вердикт для конкретного файла, локально не встановлено. Також не можна підтвердити, що репутація пояснює окреме попередження Defender. Технічної підстави змінювати production або перебудовувати ASI за результатом цього порівняння немає.

Якщо надійде подія Code Integrity чи Protection History, зіставити її шлях, час і ідентичність із контрольним файлом. Для перегляду можливої хибної класифікації допустимий шлях — перевірка точного ASI в Microsoft Security Intelligence за окремим дозволом. Результат від зовнішнього джерела може уточнити цей висновок незалежно від роботи над Camera Lifecycle.

## Поглиблений перегляд native шляхів

| Межа | Результат |
| --- | --- |
| Встановлення та відкат | Cinematic і Zoom мають окремі межі публікації готовності. Діагностичний Cinematic consumer перевіряє фактичні relocation spans і відкидає перетини. Виявлено відсутність відповідної перевірки у пари Dialogue PRE/POST. |
| Trampoline і сторінки | Довгий jump SafetyHook може зайняти більше за шість байтів основного виклику Dialogue. POST на `call+6` тоді опинявся всередині ділянки основного патча. Тепер основний hook створюється вимкненим. POST допускається лише на підтвердженому поверненні того самого виклику за фактичної довжини основного патча 6 байтів і в межах `.text`. За відмови основний hook лишається придатним. |
| Адреси та нативна пам'ять | Виправлено `IsExecutable`, який знімав модифікатори прав перед класифікацією і приймав `PAGE_GUARD`. Тепер потрібна committed executable page без guard. Для camera data переглянуто `VirtualQuery`, межі регіону, readable/writable передумови й передавання перевірених адрес. Сама перевірка прав не доводить lifetime довільного об'єкта рушія. |
| Винятки, ресурси і потоки | Native entry має `noexcept` wrapper та RAII допуск. Контрольоване завершення закриває допуск, чекає callbacks і workers, потім скидає hook owners. Переглянуто capability gates для нових спостерігачів і rollback, обмежені вікна запису та володіння ручними capture events. Динамічне вивантаження DLL не перевірялося. |
| Файли | Після відкриття резервного логу збій виділення пам'яті під рядок `OutputDebugStringW` міг повернути помилку попри відкритий handle. Форматування тепер виконується як необов'язкова діагностика після успішного відкриття. Ліміт розміру й правила спільного доступу збережені. |
| PE-захисти | Обидва точні релізні файли мають high-entropy ASLR, dynamic base, NX і security cookie. У DLL characteristics обох немає прапорця CFG. У перевірених файлах не видно регресії цих параметрів з v3.2.2 до v4. |

Технічні правки вище випливають із конкретних передумов hook або логування. Даних про їхній зв'язок із 4556 немає. Окремо пройшли focused cutover Diagnostics OFF/ON і native diagnostic-work, включно з реальними trampoline у fixture та перевірками відхилення перетину, стороннього continuation і guard page. Worker lifecycle harness пройшов сценарії конфлікту логів, повторного використання й очищення резервного файла та нормального DLL exit. Відмову виділення в необов'язковому форматуванні окремо не ін'єктували. Для останнього focused build і запущених harness підтверджено завершення власних дерев процесів.

## Локальний Defender

Штатний `MpCmdRun.exe` з платформи `4.18.26100.4-0` просканував окремі копії точних ASI з обох релізних ZIP. Обидва запуски повернули 0 і `found no threats`. Хеші збіглися до й після сканування, завершення процесів перевірено. Сканування перевіряє локальний Defender Antivirus і не відтворює рішення Application Control при завантаженні на ПК автора. ## Повторна перевірка публікації hooks і логування

Встановлення основних production camera hooks тепер використовує спільну перевірку адрес і фактичних ділянок `original_bytes()`, які SafetyHook переносить у trampoline. Перевірено Zoom IN/OUT, Cinematic aspect/ENTER/EXIT, blend activation і consumer, primary Writer, post-store та post-helper, Dialogue PRE/POST. Порівняння відхилень від початку ділянки не потребує додавання довжини до адреси. Суміжні неперекривні ділянки дозволено. Перевірка Cinematic і Zoom виконана до спільної публікації, а опційний спостерігач із конфліктом пропускається до enable. Для Dialogue збережено вузьку перевірку повернення після шестибайтового виклику.

Fault injection у тесті резервного логу кидає `std::bad_alloc` із необов'язкового репортера після успішного відкриття файла. Тест перевіряє, що відкритий handle лишається придатним до запису й повертається успішний результат.

Ін'єкція пройшла у фінальному `test.cmd -NonGraphics`. Результат 64/64 PASS з одним hardlink SKIP, WARP не запускався. Native adapter пройшов 232 ізольовані запуски. Завершення власних дерев процесів перевірено.

## App Control, Smart App Control і права читання

- Після запуску дозволеної read-only перевірки поза обмеженим середовищем обидва канали стали доступні. За десять днів вибрані ID дали 1 187 подій Code Integrity (3033, 3076, 3077, 3089, 3091, 3092) і 5 подій Defender (1116, 1117, 1120). XML цих записів не містить `STALKER2CameraTweaks` або `Stalker2-Win64-Shipping`. Це локальна вибірка. Подію іншого ПК вона не замінює. Позитивний результат читання не вимагав змін до ACL чи політик.
- Запит статусу Windows Sandbox і Hyper-V через `Get-WindowsOptionalFeature` вимагає підвищення Windows. `CiTool -lp -json` повернув `0x80070005`. Команди гіпервізора та запуск Sandbox не виявлені в доступному середовищі. Придатну ізольовану Windows із перевіреним enforced станом репутаційної політики тут не підтверджено. Значення локального `VerifiedAndReputablePolicyState` дорівнює 0, але сам запис не встановлює набір завантажених політик.
- Контрольний запуск слід проводити у відокремленій чистій Windows 11 із підтвердженим SAC enforcement або потрібною штатною App Control політикою. В обох прогонах потрібні однаковий loader, залежності й контекст завантаження, точні ASI з ZIP, збережені SHA-256 та source/Zone.Identifier, PID, час і Win32 result. Код `4556`, подію 3077 і 3089 зі спільним ActivityID зіставити зі шляхом файла. Результат audit 3076 та запуск у середовищі без перевіреної політики описувати окремо. У цьому сеансі запуск не відбувся. ## Підпис і походження релізу

У Windows SDK доступний SignTool. `verify /pa` повернув `No signature found` для обох ASI, чиї SHA-256 збігаються з вкладеннями контрольних ZIP. У перевірених сховищах `CurrentUser/My` та `LocalMachine/My` сертифікатів code signing немає. Для публічного релізу придатний Authenticode через довіреного публічного CA або Microsoft Artifact Signing Public Trust за наявності відповідної ідентифікації. Microsoft обмежує Public Trust для фізичних осіб США й Канадою. Право цього видавця на конкретну програму не перевірялося. [Підпис для Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control) · [Вимоги Artifact Signing](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)

Для майбутнього окремого рішення про реліз використовувати підпис кінцевого ASI з SHA-256 і часовою міткою RFC 3161, верифікацію Authenticode, потім пакування і незалежну звірку підпису та SHA-256 вкладеного файла. Маніфест походження має прив'язати SHA-256 архіву й ASI до Git commit, профілю, toolchain і контрольованого процесу збірки. Хеш і маніфест дозволяють звірити файл, а Authenticode додає автентифікацію видавця. Підпис не доводить відсутності детекції або конкретного рішення про 4556. Поточні релізні файли не перепідписувалися. [SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool) · [Мітки часу Authenticode](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures)
