# Cinematic Runtime State Differential Trace — Task Plan

Status: In progress — the bounded `+0x254` and recalculation branches are closed negative; natural exit write-origin is confirmed and `FUN_146B6734C` is established as a callback/lifecycle handler. Its registration/setup path is identified; the active bounded branch is the event source, subscription lifecycle and trigger condition that dispatches it during natural cinematic exit.

## Current active objective

Resolve the event source, subscription lifecycle and trigger condition that dispatch `FUN_146B6734C` during the natural cinematic exit in executable 2.0.3, without invoking or modifying the function. This is the only active research frontier in the current task.

## Historical objective

Use the confirmed live camera object and manual state transitions to identify the smallest camera/view/projection state difference between:

- constrained `16:9 / 2560x1440`, where cinematic framing is correct;
- native `32:9 / 5120x1440`, where cinematic framing is incorrect.

The result must identify concrete changed fields or derived structures that can be traced back to their writer/consumer before any implementation decision.

## Established evidence and current state

- Executable: game 2.0.3, SHA-256 `81961B7281C7CF528CE49C549CE086FCC684BD676F32FAF042BC743D939E3C69`.
- Cinematic A/B object and stable gameplay camera source were runtime-confirmed as the same object in repeated runs.
- Gameplay two-pass can execute on that object and produces correct-looking framing only with the real constrained `16:9 / 2560x1440` render state.
- Restoring only the aspect field returns `5120x1440 / 32:9`, but the cinematic framing becomes wrong again.
- Manual Hor+ conversion produces correct cinematic framing but contaminates downstream camera handoff with a visible overshoot.
- `FUN_140186BE8` was statically rejected as movable-point-light/shadow and scene-resource processing, not cinematic camera projection.
- The bounded source/research inventory currently exposes only desktop display dimensions through `DEVMODE`; no validated game-owned `ViewRect`, `UnscaledViewRect` or internal render-size source has been established yet.
- The first bounded camera snapshot found no direct pointer-like members in `+0x200…+0x280`; the only clean reversible local change was `+0x254` (`3.5555556 → 1.7777778 → 3.5555556`).

## Approved scope

- Start from the already captured shared camera object and confirmed `+0x254/+0x259` state family.
- Prepare a diagnostic comparison of the same object across the two known control states.
- Expand only to direct pointer members of that object and one-hop camera/view structures; do not search for `ViewRect` globally in the executable.
- Compare aspect, mode/flags, render dimensions, projection scales, view rectangle, FOV-derived values and object identity/lifetime.
- Record practical render-surface dimensions from the game `window/client` bounds, alongside desktop display dimensions; retain UE `ViewRect`/internal render-size discovery as optional future evidence only.
- Use the recorded `window/client` dimensions as independent validation data for `2560x1440 ↔ 5120x1440`; do not promote them as a projection-state owner solely from the size change.
- Promote only candidates that change at the controlled `F7/F8` transition and have a reproducible writer or reader path.
- Every manual test snapshot must include automatically logged game `window/client` dimensions (`2560x1440` or `5120x1440` in the current controls), not only the aspect field and not only external NVIDIA/DLSS telemetry.
- If no such one-hop render source exists, use the next bounded fallback: snapshot the small known camera-field region and its direct child pointers across `wrong native 32:9 → correct constrained 16:9 → wrong native 32:9`; keep the resolution source branch unresolved rather than expanding the search globally.
- After the local snapshot is exhausted, trace only the writer/reader chain for `+0x254` at the controlled `wrong → correct → wrong` transition; do not enlarge the object snapshot before this access-path pass.
