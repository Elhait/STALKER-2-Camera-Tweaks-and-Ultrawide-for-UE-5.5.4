# Post-EXIT recovery — пропозиція контракту

Дата: 2026-11-11. Статус: проєкт контракту для перегляду, не прийнята production-архітектура. Цей документ не замінює `docs/ARCHITECTURE.md` або `docs/SAFETY_INVARIANTS.md` і не дозволяє зміну camera math.

Після перегляду користувач схвалив документ як основу вузького подальшого дослідження, але не production-реалізації. [Наступний branch review](../reports/POST_EXIT_NATIVE_BRANCH_FEASIBILITY_2026-11-11.md) уточнює доступність progress/activation evidence. Поведінковий oracle JSON залишається невизначеним.

## Предмет і факти

Предмет — право корекції та безперервність writer output під час передачі Cinematics → Gameplay. Не потрібно встановлювати глобальний стан усіх камер гри чи доводити, що кожен generic blend є cinematic blend.

Основа: [runtime-кореляція](../reports/POST_EXIT_BLEND_LIVE_CORRELATION_2026-11-11.md), [native data-flow](../reports/POST_EXIT_NATIVE_BLEND_DATAFLOW_2026-11-11.md), [структурований запис](../evidence/post-exit-blend-live-2026-11-11-231304/regression-fixture.json).

Підтверджено в записаних межах:

- Під час другої катсцени 1417 writer samples мають input 70 і output 108,941°.
- Після EXIT конкретний blend із start 70 і target 90,3115° звертається до тієї самої камери. Сім записаних пар пов'язують його raw output/аргумент setter із полем камери та writer input.
- Останні сусідні **записані** RuntimeCombine outputs на межі відновлення — 90,293° та 127,116° через 13 мс. Різниця 36,823°. Це не вимірювання пікселів або доказ відсутності незаписаних native calls.
- Після першого EXIT два blend-контексти мають спільний receiver і чергують виклики setter. Один тримає 90,3115°, інший рухається до 70°.
- Mod recovery після першого EXIT завершилося до завершення цих native оновлень. Отже, native blend completion і завершення mod handoff — різні події.

## Терміни та власники

| Поняття | Власник / доказ | Що не випливає з нього |
|---|---|---|
| Cinematic generation/source authority | Прийнятий lifecycle та підтверджена source association | Ексклюзивне право конкретного native blend на камеру |
| Native blend activation | Конкретний native екземпляр і його актуальна активація | Що його ініціалізував EXIT; що адреса ніколи не використовується повторно |
| Setter invocation | Поточний receiver, native call contract та фактичний аргумент | Що цей запис останній до writer або що setter вже повернувся |
| Writer invocation | Поточні source/output/input і валідований writer contract | Що input має native-space походження лише тому, що його прочитала гра |
| FOV space/provenance | Свідчення походження конкретного значення | Це не властивість pointer або всіх samples generation |
| Rendered-domain endpoint | Підтверджений результат корекції на релевантній writer-межі | Фінальні пікселі на екрані без окремого спостереження |
| Mod handoff complete | Дозволений перехід до Gameplay-політики з узгодженим виходом | Native blend завершився або виконав cleanup |

Production runtime володіє рішенням про корекцію. Native механізм володіє своїм часом, easing та порядком викликів. Діагностика лише показує доступні факти; її лічильники, журнал або ввімкнення не можуть бути джерелом production authority.

## Інваріанти майбутньої реалізації

1. **Право та простір — окремі перевірки.** Прийнята generation/source дозволяє розглядати sample; не надає йому автоматично тег Native. Збіг із 70, cached cinematic output або EXIT target не є доказом походження.
2. **Право застосовується до поточного виклику.** Не переносити свідчення іншої камери, generation, активації blend або старого writer. Не розіменовувати кешований output чи завершений blend.
3. **Кілька контекстів допустимі.** Не обирати перший blend як єдиного власника. Спільний receiver не є конфліктом, а різний target не означає автоматично сторонню камеру. Враховувати фактичний native порядок; не змінювати його.
4. **Адреса не є activation token.** Для збереженого стану потрібна підтверджена актуальність або invocation-local свідчення. Pointer equality, час від EXIT чи незмінний start/target не замінюють цього контракту.
5. **Не змінювати native clock/easing.** Без таймерів, frame-count delays, примусового продовження blend чи згладжування, яке приховує втрату доказів. Прогрес уже eased native sample не потрібно пропускати через easing вдруге.
6. **Не застосовувати HorPlus двічі.** Результат відомого mod transform не може ставати native baseline або повторним входом HorPlus. Unknown не перетворюється на Native через числовий діапазон.
7. **Узгоджений handoff.** Для одного безперервно підтвердженого переходу зміна coordinator/recovery policy сама по собі не повинна перемикати output із native pass-through на transformed FOV. Рішення на обох боках handoff має бути сумісним із тим самим актуальним sample/provenance.
8. **Endpoint — не весь lifecycle.** Наближення input до target може бути свідченням досягнення числової межі. Воно не доводить завершення native blend, відсутність інших контекстів або їх cleanup. Водночас mod handoff не зобов'язаний чекати native cleanup, якщо Gameplay вже має достатнє право та узгоджену mapping-політику.
9. **Умовна безперервність.** Для непідтвердженого sample зберігається pass-through. Гарантувати одночасно native pass-through і довільний безперервний transformed output неможливо. Втрата доказів є явною деградацією з bounded-діагностикою; її не маскують утриманням старого FOV. Вимога безперервності стосується підтвердженого переходу, а не будь-якого camera cut.
10. **Локальна відмова.** Невідомий blend/sample не знищує автоматично валідну source association. Справжній source/aspect conflict і нова generation зберігають чинну інвалідацію; попередні свідчення не оживають.
11. **Зміни налаштувань явні.** Новий ENTER, вимкнення Cinematics/Gameplay, зміна режиму, source replacement і скасування переходу мають окремі disposition. Не застосовувати старий mapping після цих меж. При цьому історичний native контекст може продовжувати існувати без права мода його коригувати.
12. **Незалежність capability.** Production-контракт не залежить від Diagnostics або користувацької Dialogue policy. Відсутність допоміжного native evidence вимикає лише залежну інтервенцію, без SHA/version allowlist і без відключення незалежних можливостей.

## Математична розвилка

Позначення: `H_a(f)` — існуючий HorPlus для aspect `a`; `S,T` — підтверджені start/target конкретної native активації; `u` — native eased weight; `C` — релевантний останній підтверджений cinematic output.

### A. HorPlus кожного підтвердженого native-space sample

```text
f = native sample, уже після native easing
y = H_a(f)
```

Це зберігає застосування HorPlus до кожного native FOV. Не потребує відтворення native easing або знання кожного caller. Але вимагає доказу Native для поточного input; на transformed-start траєкторії цей доказ не можна вигадати.

### B. Відображення native eased progress між output endpoints

```text
y = C + (H_a(T) - C) * u
```

Це зберігає native eased weight у transformed/output-domain переході та не трансформує проміжний untagged FOV повторно. Потрібні докази релевантності `C`, нативного призначення `T`, актуальної активації та відповідного `u`. Сам native start не обов'язково треба повторно перетворювати, але не можна підставляти довільний кешований cinematic endpoint до іншого blend.

Не обов'язково спостерігати duration і заново реалізовувати easing, якщо валідований native branch справді гарантує `f = S + (T-S)*u`: тоді можливе обчислення `u = (f-S)/(T-S)` із поточного підтвердженого state. Це **пропозиція для перевірки branch contract**, а не дозвіл розпізнавати ownership за FOV-діапазоном. Для інших формул, degenerate `S=T`, недоступних полів або іншого branch цей висновок не діє автоматично. Загального правила затискання невідомого `u` у [0,1] тут немає.

### Числова різниця

Нижче математичні приклади, а не нові вимірювання native progress:

| Вхідні умови | `u` | A: transform sample | B: mapping endpoints |
|---|---:|---:|---:|
| 32:9, `S=70`, `T=90,3115`, `C=H(70)` | 0 | 108,941° | 108,941° |
| Ті самі умови | 0,5 | 118,560° | 118,030° |
| Ті самі умови | 1 | 127,119° | 127,119° |
| Старий fixture: 3440×1440, `S=C=106,688`, `T=90` | 0 | **122,044°**, якщо помилково вважати input Native | 106,688° |
| Старий fixture, ті самі умови | 0,5 | 114,518°, за тієї самої помилкової класифікації | ≈106,688° |
| Старий fixture, ті самі умови | 1 | ≈106,688° | ≈106,688° |

Старий сценарій походить із `TestRecordedRecoveryInterpolationRemainsInHorPlusSpace` у `tests/cinematics/horplus_post_exit_recovery_harness.cpp`, де aspect дорівнює **3440/1440**, а не 32:9. Його native instance/progress не зафіксовані в новому capture. Наявний expected output лишається контрольним контрактом цього fixture, а не доказом універсальної семантики гри.

Рішення між A і B у цьому документі **не прийнято**. Це не обов'язково один глобальний вибір: єдина policy може допускати A для підтвердженого Native sample та B для іншого підтвердженого mapping contract. Відсутність розриву на endpoints не робить їхню проміжну поведінку еквівалентною.

### Метод mapping є частиною admission scope

Допустимий спосіб обчислення фіксується для підтвердженого transition/admission scope, а не вибирається заново за зручністю кожного callback. Scope має визначатися реально доступною lineage/freshness, не лише адресою камери або першим blend у generation. Кілька контекстів можуть мати окремі scope на спільному receiver.

Під незмінними admission, provenance та native facts зміна лише coordinator або стану recovery не змінює mapping method. Втрата доказів не дозволяє непомітно перейти з B до A чи навпаки: це явна деградація/cancellation. Не можна продовжувати старий FOV, щоб приховати втрату права на обчислення.

Зміна методу потребує підтвердженої межі нового admission scope або доведеної еквівалентності результатів у відповідній межі. Наприклад, аналітично узгоджений endpoint може бути такою межею за належного provenance; довільна близькість чисел — ні. У середині прикладу 32:9 перемикання A/B саме створило б зміну приблизно 0,530° без нової native події.

Фіксація методу не означає фіксації native duration/easing. Гра може змінювати власні параметри під час tick; це не дозвіл моду ігнорувати ці зміни. Якщо актуальний branch більше не відповідає доведеному contract, доступність mapping потрібно переоцінити явно.

Велика різниця FOV сама по собі не позначає ні помилку безперервності, ні native camera cut. Для класифікації cut потрібна незалежна native подія/lineage. Непідтверджена зміна залишається невизначеною, а не вигаданим cut для проходження тесту.

## Мінімальні відсутні докази — залежно від рішення

| Доказ | Для A | Для B | Що не потрібно вимагати без залежності |
|---|---|---|---|
| Поточне source/generation admission та freshness | Потрібно | Потрібно | Власник усіх камер гри |
| Native-space походження поточного writer sample | Потрібно | Не потрібне як універсальний тег, якщо є коректна progress-to-output mapping | Класифікація лише за числом FOV |
| Зв'язок активного native state/weight з поточним результатом | Лише якщо на ньому будується space proof | Потрібно для mapping | Ексклюзивність одного blend на receiver |
| Актуальні output endpoints для цієї активації | Handoff має зберігати узгоджений output | Потрібно | Перший знайдений cinematic cache без актуальності |
| Конкретний EXIT caller | Лише для caller-specific admission | Потрібна достатня lineage для cinematic-specific endpoints; caller — один можливий спосіб | Повний граф усіх callers як обов'язкова передумова будь-якої корекції |
| Native completion callback | Лише якщо він керує disposition | Лише якщо він керує disposition | Очікування cleanup для handoff, який уже безпечний за власним контрактом |
| Прямий readback після setter | Не автоматична передумова writer-only корекції | Потрібен лише якщо рішення покладається на факт цього запису | Новий hook тільки для формальної повноти журналу |

Наступне вузьке дослідження має перевірити доступну lineage та придатність native branch до B, зіставляючи її з потребою native-space proof для A. Не потрібні загальні camera logs, пошук weapon names або новий глобальний архітектурний аудит. Наявний capture вже достатній для characterization поточного дефекту та перевірки порядку interleaved observations.

## Регресійні входи та майбутні acceptance checks

| Вхід / зміна | Що має перевіряти майбутній тест |
|---|---|
| Збережений `70 → 90,3115` із сімома парами | Реальні input/state подаються у production helper; він більше не створює штучний policy cliff на handoff за встановленого admission |
| Старий `106,688 → 90`, aspect 3440/1440 | Не з'являється другий HorPlus; зберігається узгоджений раніше output, якщо контракт не переглянуто явно |
| Два blend-контексти на одному receiver | Право не закріплюється за першим; враховується поточна invocation, supersession і native порядок |
| `S=T`, новий target або rearm за тією самою адресою | Немає ділення на нуль, старого progress чи автоматичного відновлення identity |
| Native-space / transformed-space / unknown | Різні provenance не зливаються за рівністю чисел; unknown залишається локальним pass-through |
| Source replacement, новий ENTER, stale generation | Попереднє evidence не дозволяє нову корекцію |
| Вимкнення, зміна режиму та втрата capability | Явні cancellation/handoff без використання старого mapping |
| Diagnostics OFF/ON та Dialogue OFF/ON | Однакове production-рішення за однакових доступних native facts |
| Той самий sample/evidence, змінено лише coordinator recovery→Gameplay | Mapping method та результат не змінюються без окремої підстави |
| Спроба A↔B усередині чинного scope | Перехід відхиляється або має явну підтверджену межу; схожість сусідніх outputs не достатня |
| Підтверджений native cut | Тест не вимагає штучно безперервного output і не приховує реальну зміну камери |
| Втрата provenance під час переходу | Немає утримання cached FOV або неявної підміни A/B заради візуального згладжування |

Новий JSON fixture є **input/evidence**, а не затвердженим oracle майбутнього output. Його verifier перевіряє hash/рядки/зв'язки/числові факти, але не запускає production recovery і не підтверджує виправлення. Поведінковий regression додається після вибору контракту; тести не повинні підсовувати production вигадані `trusted` flags, які він не може встановити.

## Результат цього етапу

- Збережено raw capture та структурований fixture із 66 посиланнями на записи, сімома кореляціями, точною межею resumption і interleaving witness.
- Визначено інваріанти та умовні вимоги до A/B; production-контракт ще не змінено.
- Verifier цілісності та чотири негативні integrity cases пройшли. Це не PASS camera recovery.
- Немає production edits, нової ASI-збірки, native/graphics tests, запуску гри, debugger або Git-операцій.
