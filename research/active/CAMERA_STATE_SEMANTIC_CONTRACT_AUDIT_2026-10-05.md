# Camera State / Camera Integration semantic contract audit

**Date/status:** 2026-10-05; read-only audit and implementation plan, not an implemented fix. **Scope:** presentation/provenance only; no camera-correction policy, F1–F8 finding, engine identity, or renderer architecture changes. Current inspected source is the dirty workspace; the referenced A03C78… production artifact and 58/58/build result are earlier reported validation, not validation performed for this document.

## Evidence vocabulary and end-to-end path

- **CODE-PROVEN:** directly established by the current source and its call order. **RUNTIME-OBSERVED:** supplied log/screenshots only. **PRODUCTION-EQUIVALENT (PE):** scenario traverses the shared production transaction/primitive to its decision. **INFERRED:** reasonable consequence not independently observed. **UNKNOWN:** present evidence cannot establish the claimed engine/visible-camera semantics.
- Writer hook validates/captures RSI/RBX, raw XMM0 FOV, `RSI+0x254` aspect and `RSI+0x259` flags; `ProcessCameraWriter` / Gameplay policy creates input/result FOV observation. `PublishCameraStateSnapshot` feeds `PublishCameraStateSnapshotLocked`, which copies groups and marks per-group freshness. `NotifyOverlayCameraStatePublished` requests a visible-overlay redraw. `ReadOverlaySemanticSnapshot` copies the camera snapshot and independently reads settings, coordinator, capability, active cinematic selection, Dialogue phase, baseline usability and client-window aspect. `ProjectCameraIntegration`, `Project*Presentation`, `DrawCameraStateView`, renderer labels and localization turn them into visible assertions. [CODE-PROVEN: `src/plugin/runtime.cpp`, `src/plugin/camera_writer_transaction.hpp`, `src/camera/camera_state_publication.hpp`, `src/overlay/*`].
- Important ordering: snapshot publication occurs before the hook adapter writes returned FOV to XMM0. The snapshot contains the **selected production policy result**, not a readback of the engine's final visible projection. The result normally precedes the local XMM0 commit, but neither final camera FOV nor projection aspect is measured here. [CODE-PROVEN / UNKNOWN final visible state].
- The semantic read combines state captured at different boundaries. `SnapshotFreshness::Current` means current under that group's mod-defined invalidation rules, not a simultaneous camera/world snapshot. `cameraStateValid` only means a container was published. [CODE-PROVEN].

## Concrete semantic mismatches, ordered by impact

1. **[CODE-PROVEN + RUNTIME-OBSERVED] Aspect-domain conflation.** `HorPlus FOV` is live production output for writer-observed aspect 3.0 while the displayed client ratio is 2.3889/1.7778. `locales/en.json` tooltip says it is for “current viewport”. That wording is false in this capture. No evidence the correction itself is wrong or that 119.27 is final visible FOV.
2. **[CODE-PROVEN] “Aligned” overstates evidence.** Comparison is configured cinematic target vs window ratio plus configured policy/capability/baseline predicates. It neither reads actual cinematic aspect nor verifies final Gameplay/cinematic camera paths. It also does not use active latched cinematic mode, which can differ from the configured next-ENTER mode. Current `DetailAligned` and aspect tooltip claim more than their inputs establish.
3. **[CODE-PROVEN] Source-stage ambiguity.** `Native FOV` means writer hook input; `HorPlus FOV` means pre-XMM-commit policy result; `Gameplay FOV` means retained neutral estimate. They are presented together under one FOV heading without enough stage/context labeling. None proves final visible FOV.
4. **[CODE-PROVEN] Dead or lossy rows.** Presentation epoch, generation presentation epoch, Dialogue target/source are unpopulated in production; configured Gameplay FOV is explicitly unknown. Flags row has no own validity/freshness indicator. Existing copy-only tests can populate dead fields artificially.
5. **[CODE-PROVEN / impact INFERRED] Mixed-time status.** Camera snapshot is published at writer boundary while settings/coordinator/window ratio are read later. F9 group freshness prevents many inherited values being presented as Current, but there is no cross-group atomic camera state. Active vs requested cinematic policy is an especially concrete mismatch. UI should state which clock a row uses, not pretend one coherent frame.
6. **[UNKNOWN] Actual final visible FOV, final projection aspect and native camera object identity.** No current dataflow proves these. Absence of those facts is not itself a correction defect. Do not manufacture them via window ratio, RSI, `identityEpoch`, publication sequence, elapsed time, or FOV equality.

## F9 transport/freshness assessment

`CameraStateSnapshot` is adequate as a **transport container of last observations**, not a monolithic current camera truth. Seven freshness groups, source-scoped retained confirmation and explicit invalidation on writer/settings/lifecycle/zoom transitions are useful and remain intact. Publication updates only facts supplied by that transaction and need not rebind retained A to B; existing F9 PE test covers the A×3→Gameplay OFF→B edge. The group model does not encode the aspect context of policy output in the Integration row (although the same publication carries `evidence.aspect`), does not expose flags validity, and lets an actively changing mod-state member share stale zoom/Dialogue group metadata. First remedy is **projection contract and labels using existing fields**; add only narrow validity/context metadata where a deterministic negative control proves the existing transport insufficient. A generic universal fact/epoch type is not justified. `identityEpoch` is a writer-pair observation epoch, not CameraLifetime; `eventSequence` is publication count. No timeout/frame-age invalidation.
