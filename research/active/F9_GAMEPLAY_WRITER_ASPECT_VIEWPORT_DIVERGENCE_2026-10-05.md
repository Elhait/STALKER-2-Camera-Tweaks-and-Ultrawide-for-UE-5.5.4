# F9 — Gameplay writer aspect vs client viewport aspect (read-only causal audit)

Status: **OPEN — insufficient evidence to classify the correction as defective**. No production, harness, configuration, localization, build, or game change was made in this audit.

## Independent client aspect contract

`ReadOverlaySemanticSnapshot` invokes `ReadCurrentProcessClientViewportAspect()` at semantic read time. The Win32 helper prefers the foreground window if owned by this process, otherwise discovers a current-process window, calls `GetClientRect`, checks dimensions at least 16×16, and returns **client-area width/height** or NaN. [CODE-PROVEN: `src/platform/win32/viewport.cpp`, `src/plugin/runtime.cpp`]. This is a window geometry measurement, not render-resolution or final projection readback. Letterboxing, internal rendering/upscaling, a constrained camera, multiple candidate windows or transient resize can make camera/projection aspect differ from the client ratio. Cinematic Auto uses a related helper with a display-resolution fallback; that does not promote the client ratio to Gameplay HorPlus authority.

The Overlay log records later surface dimensions `4320×1440` (3.0), `4096×1152` (3.55556), and `2560×1440` (1.77778), matching the screenshots' client-ratio classes. [RUNTIME-OBSERVED] Its QPC-only resize records are not mapped to the wall-clock camera-log transition; no causal ordering between those specific resize records and the `19:12:46.397` field change is claimed.

## Competing causes, ordered by available evidence

1. **Distinct camera-property and client-window domains** — supported by the separate production readers and the historical 32:9 counterexample. Whether `3.55556` is the correct camera/projection context *in this run* remains unknown. [CODE-PROVEN + HISTORICAL RUNTIME; CURRENT SEMANTICS UNKNOWN]
2. **Native or settings-side field update at the first aspect transition, then no later update despite client resizes** — consistent with same RSI, `1.77778→3.55556`, and later repeated reads; no exact native writer/call stack or update obligation has been shown. [RUNTIME-OBSERVED + INFERENCE]
3. **Mod-owned aspect write/restore surviving a later window change** — source paths exist, but the active HorPlus transition shows no corresponding logged action; cannot rule out without write provenance. [CODE-PROVEN POSSIBILITY, RUN-SPECIFIC CAUSE UNPROVEN]
4. **Wrong HorPlus formula or stale Overlay cache** — contradicted for the observed `90.6557→127.393` sample by the formula and live ADS-dependent policy output. This excludes those narrow explanations, not a wrong input-domain choice. [CODE-PROVEN + RUNTIME-OBSERVED]

**Verdict:** `insufficient evidence`. A **live HorPlus correction using writer aspect 3.55556 while client geometry changes** is confirmed; a Gameplay HorPlus defect is not yet confirmed. The missing proof is whether `RSI+0x254` is supposed to track the current correction/projection aspect through the later resolution changes, and who wrote/retained it. The aspect numbers alone cannot supply that contract. F9 stays OPEN. Do not substitute `ClientViewportAspect`, add age heuristics, or compute a nicer number in Overlay.

## Smallest discriminating follow-up (not executed)

In **one user-authorized exact-image runtime session**, after validating the game/ASI identities and observing the live Gameplay writer RSI, place a scoped hardware **write** breakpoint on that receiver's `RSI+0x254` (four bytes). For each hit record instruction address/module, call stack, old/new float, receiver RSI, nearby flags `+0x259`, current Gameplay mode/coordinator, and client rectangle. Log independent resize/settings events and a writer callback immediately before/after each controlled `3.55556→1.77778→3.55556` window transition. Re-arm if the receiver changes; do not watch arbitrary pointer chains or write the field. If the responsible write is inside the ASI, map it to its production transaction. If native, inspect the *bounded* writer/caller input and whether that event fires on the reverse resize. If no field write occurs, establish whether native view/projection consumes this stored aspect or intentionally uses a different output aspect. Only a demonstrated mismatch between the field's intended correction contract and its use would justify a policy fix. No new hook or production instrumentation is authorized by this report.
